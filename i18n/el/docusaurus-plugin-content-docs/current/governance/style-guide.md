# Open Manuscript Initiative Οδηγός στυλ προδιαγραφών

## Μεταδεδομένα εγγράφου

| Πεδίο | Τιμή |
|---|---|
| Τύπος εγγράφου | Πολιτική διακυβέρνησης |
| Κατάσταση | Πρόχειρο |
| Έκδοση | 0.1.0 |
| Κανονιστική γλώσσα | Αγγλικά |
| Ισχύει για | Προδιαγραφές, προφίλ, μητρώα, σχήματα, παραδείγματα και σχετική τεχνική τεκμηρίωση τουOMI |

## 1. Σκοπός

Ο παρών οδηγός καθορίζει τις συντακτικές, δομικές, ορολογικές και τεχνικές συμβάσεις που χρησιμοποιούνται από το «Open Manuscript Initiative» (OMI).

Σκοπός του είναι να διασφαλίσει ότι τα έγγραφα OMI:

- ακριβής·
- εσωτερικά συνεπής·
- ανεξάρτητο από την υλοποίηση·
- προσιτό σε αναγνώστες από διάφορους επιστημονικούς κλάδους·
- κατάλληλο για τυποποιημένη τεχνική χρήση·
- σταθερό όσον αφορά τη διαχείριση εκδόσεων και τη μετάφραση·
- εύκολο να αναθεωρηθεί, να δοκιμαστεί, να αναφερθεί και να συντηρηθεί.

Οι συγγραφείς και οι επιμελητές των τεχνικών εγγράφων του «OMI» ΠΡΕΠΕΙ να ακολουθούν τον παρόντα οδηγό, εκτός εάν σε κάποιο έγγραφο αναφέρεται ρητά και αιτιολογείται κάποια εξαίρεση.

## 2. Πεδίο εφαρμογής

Ο παρών οδηγός ισχύει για:

- έγγραφα με τον κωδικό «`OMI-SPEC-*`»·
- πολιτικές διακυβέρνησης·
- προφίλ υλοποίησης·
- μητρώα και ελεγχόμενα λεξιλόγια·
- JSON Σχήματα και τεκμηρίωση σχημάτων·
- απαιτήσεις συμμόρφωσης·
- δείγματα εγγράφων και εξαρτήματα δοκιμών·
- αντιστοιχίσεις διαλειτουργικότητας·
- οδηγοί μετανάστευσης·
- επίσημες μεταφράσεις.

Οι ανεπίσημες ανακοινώσεις έργων, τα εκπαιδευτικά βίντεο, οι αναρτήσεις σε ιστολόγια και οι συζητήσεις της κοινότητας ΘΑ ΠΡΕΠΕΙ να ακολουθούν τους κανόνες ορολογίας του παρόντος οδηγού, αλλά δεν είναι υποχρεωτικό να χρησιμοποιούν το πλήρες πρότυπο προδιαγραφών.

## 3. Κανονιστική γλώσσα

Οι λέξεις-κλειδιά **ΠΡΕΠΕΙ**, **ΔΕΝ ΠΡΕΠΕΙ**, **ΑΠΑΙΤΕΙΤΑΙ**, **ΘΑ**, **ΔΕΝ ΘΑ**, **ΘΑ ΠΡΕΠΕΙ**, **ΔΕΝ ΠΡΕΠΕΙ**, **ΣΥΝΙΣΤΑΤΑΙ**, **ΔΕΝ ΣΥΝΙΣΤΑΤΑΙ**, **ΜΠΟΡΕΙ** και **ΠΡΟΑΙΡΕΤΙΚΟ** πρέπει να ερμηνεύονται ως όροι κανονιστικών απαιτήσεων όταν, και μόνο όταν, εμφανίζονται με κεφαλαία γράμματα.

OMI Τα έγγραφα ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν κατά προτίμηση το ακόλουθο υποσύνολο:

- **ΠΡΕΠΕΙ** και **ΔΕΝ ΠΡΕΠΕΙ** για τις απαιτήσεις απόλυτης διαλειτουργικότητας ή συμμόρφωσης·
- **ΠΡΕΠΕΙ** και **ΔΕΝ ΠΡΕΠΕΙ** για ισχυρές συστάσεις με βάσιμες εξαιρέσεις·
- **MAY** για επιτρεπόμενη προαιρετική συμπεριφορά·
- **ΣΥΝΙΣΤΑΤΑΙ** όταν η πρόζα ακούγεται πιο φυσική από ό,τι το **SHOULD**·
- **ΠΡΟΑΙΡΕΤΙΚΟ** όταν περιγράφεται ένα προαιρετικό στοιχείο ή πεδίο και όχι η συμπεριφορά κατά την υλοποίηση.

### 3.1 Βαθμός απαίτησης

Μια **ΑΠΑΡΑΙΤΗΤΗ** προϋπόθεση:

- είναι απαραίτητο για τη συμμόρφωση, τη διαλειτουργικότητα, την ακεραιότητα ή την ασφάλεια·
- μπορεί να ελεγχθεί ή να αξιολογηθεί αντικειμενικά·
- δεν εκφράζει απλώς μια εκδοτική προτίμηση.

Μια απαίτηση **SHOULD**:

- καθορίζει την αναμενόμενη συμπεριφορά·
- επιτρέπει εξαιρέσεις μόνο όταν οι συνέπειες είναι γνωστές·
- ΘΑ ΠΡΕΠΕΙ να περιγράφονται αυτές οι συνέπειες, όπου αυτό είναι εφικτό.

Μια δήλωση για τον **Μάιο**:

- χορηγεί άδεια·
- δεν συνιστά σύσταση·
- ΔΕΝ ΠΡΕΠΕΙ να χρησιμοποιείται για να περιγράψει αβέβαιη συμπεριφορά.

### 3.2 Αποφύγετε τις ασαφείς λέξεις στις απαιτήσεις

Τα κανονιστικά έγγραφα ΘΑ ΠΡΕΠΕΙ να αποφεύγουν τη χρήση των ακόλουθων λέξεων χωρίς περαιτέρω διευκρινίσεις:

- συνήθως·
- γενικά·
- συνήθως·
- κατάλληλο·
- λογικό·
- επαρκής·
- απλό·
- προφανές·
- φιλικό προς τον χρήστη·
- αποδοτικό·
- ασφαλής;
- πρότυπο.

Όταν απαιτείται η χρήση τέτοιων όρων, το έγγραφο ΠΡΕΠΕΙ να καθορίζει μετρήσιμα κριτήρια ή να εξηγεί το πλαίσιο λήψης της απόφασης.

Κακό:

> Οι υλοποιήσεις θα πρέπει να αποθηκεύουν τους αναγνωριστικούς κωδικούς κατάλληλα.

Καλύτερα:

> Οι υλοποιήσεις ΠΡΕΠΕΙ να διατηρούν τις τιμές των αναγνωριστικών χωρίς να αλλάζουν τα κεφαλαία και τα μικρά γράμματα, τα σημεία στίξης ή την κωδικοποίηση με ποσοστά, εκτός εάν η προδιαγραφή του αναγνωριστικού ορίζει ρητά έναν κανονικό μετασχηματισμό.

### 3.3 Μία απαίτηση ανά πρόταση

Οι κανονιστικές προτάσεις ΠΡΕΠΕΙ να εκφράζουν μία απαίτηση που μπορεί να ελεγχθεί ανεξάρτητα.

Κακό:

> Μια εφαρμογή ΠΡΕΠΕΙ να επαληθεύει την εγγραφή, να εμφανίζει τα σφάλματα και να διατηρεί τις άγνωστες ιδιότητες.

Καλύτερα:

> Μια εφαρμογή ΠΡΕΠΕΙ να επαληθεύει την εγκυρότητα της εγγραφής σε σχέση με το δηλωμένο σχήμα.
>
> Μια υλοποίηση ΠΡΕΠΕΙ να αναφέρει τις αποτυχίες επικύρωσης.
>
> Μια υλοποίηση ΠΡΕΠΕΙ να διατηρεί τις άγνωστες ιδιότητες επέκτασης κατά τη διάρκεια μιας διαδρομής χωρίς απώλειες.

### 3.4 Αναγνωριστικά απαιτήσεων

Οι προδιαγραφές που βρίσκονται σε κατάσταση **Υπό αξιολόγηση** ή σε μεταγενέστερη κατάσταση ΘΑ ΠΡΕΠΕΙ να αποδίδουν σταθερούς αναγνωριστικούς κωδικούς στις κανονιστικές απαιτήσεις.

Η συνιστώμενη μορφή είναι:

```text
REQ-<SPEC>-<NNN>
```

Παράδειγμα:

```text
REQ-DOC-001
REQ-CIT-014
REQ-VAL-023
```

Οι αναγνωριστικοί κωδικοί των απαιτήσεων ΠΡΕΠΕΙ να παραμένουν σταθεροί εντός μιας κύριας έκδοσης προδιαγραφών. Εάν μια απαίτηση καταργηθεί, ο αναγνωριστικός κωδικός της ΔΕΝ ΠΡΕΠΕΙ να ανατεθεί σε άλλη απαίτηση.

## 4. Γλώσσα και φωνή

### 4.1 Κανονιστική γλώσσα

Η επίσημη γλώσσα του OMI είναι τα αγγλικά.

Οι αγγλικές προδιαγραφές ΠΡΕΠΕΙ να χρησιμοποιούν τεχνικό κείμενο που είναι κατανοητό σε διεθνές επίπεδο. Οι συντάκτες ΠΡΕΠΕΙ να αποφεύγουν τις ιδιωματικές εκφράσεις, το χιούμορ, τις μεταφορές που σχετίζονται με συγκεκριμένες κουλτούρες και την περιττή ρητορική γλώσσα.

### 4.2 Φωνή

Οι προδιαγραφές ΠΡΕΠΕΙ να χρησιμοποιούν άμεσες δηλωτικές προτάσεις.

Προτιμώμενο:

> Κάθε εμφάνιση παραπομπής αντιστοιχεί σε μία καταχώριση της βιβλιοθήκης.

Να αποφεύγετε:

> Πρέπει να σημειωθεί ότι μια εμφάνιση παραπομπής είναι κάτι που, κατά γενικό κανόνα, αναμένεται να παραπέμπει σε μία καταχώριση της βιβλιοθήκης.

Προτιμάται η ενεργητική φωνή όταν καθιστά σαφή την ευθύνη:

> Ο επαληθευτής επισημαίνει την ιδιότητα που δεν υποστηρίζεται.

Η παθητική φωνή ΜΠΟΡΕΙ να χρησιμοποιηθεί όταν ο δράστης δεν έχει σημασία:

> Η ιδιότητα δεν περιλαμβάνεται στην κανονική έξοδο.

### 4.3 Χρόνος

Οι κανόνες συμπεριφοράς ΠΡΕΠΕΙ να διατυπώνονται στον ενεστώτα.

Προτιμώμενο:

> Ο αναλυτής απορρίπτει έναν μη έγκυρο προσδιοριστή.

Να αποφεύγετε:

> Ο αναλυτής θα απορρίψει έναν μη έγκυρο αναγνωριστικό.

### 4.4 Άτομο

Στις προδιαγραφές ΘΑ ΠΡΕΠΕΙ να αποφεύγεται η αναφορά στον αναγνώστη με το «εσείς». Αντ’ αυτού, χρησιμοποιήστε τον αρμόδιο ρόλο ή το αρμόδιο στοιχείο:

- συγγραφέας;
- συντάκτης;
- υλοποίηση·
- επεξεργαστής;
- ελεγκτής;
- renderer;
- πελάτης;
- διακομιστής;
- αποθετήριο.

### 4.5 Γλώσσα χωρίς διακρίσεις και ουδέτερη

OMI Τα έγγραφα ΠΡΕΠΕΙ να χρησιμοποιούν γλώσσα που εκφράζει σεβασμό, είναι χωρίς διακρίσεις και βασίζεται στους ρόλους. Οι αντωνυμίες που υποδηλώνουν φύλο ΠΡΕΠΕΙ να αποφεύγονται όταν το φύλο του ατόμου δεν έχει σημασία.

Τα παραδείγματα και τα δείγματα ταυτότητας ΔΕΝ ΠΡΕΠΕΙ να βασίζονται σε στερεότυπα ή να υπονοούν ότι μια συγκεκριμένη γλώσσα, περιοχή, επιστημονικός κλάδος, τύπος ιδρύματος ή μοντέλο έκδοσης αποτελεί το πρότυπο για την ακαδημαϊκή έρευνα.

## 5. Κατηγορίες εγγράφων

Κάθε τεχνικό έγγραφο της σειράς «OMI» ΠΡΕΠΕΙ να αναγράφει την κατηγορία του.

### 5.1 Προδιαγραφές

Μια προδιαγραφή καθορίζει κανονιστικές δομές, συμπεριφορές, περιορισμούς ή απαιτήσεις διαλειτουργικότητας.

Μορφή αναγνωριστικού:

```text
OMI-SPEC-NNN
```

### 5.2 Προφίλ

Ένα προφίλ επιλέγει, περιορίζει ή επεκτείνει μία ή περισσότερες προδιαγραφές για μια συγκεκριμένη κοινότητα, επιστημονικό πεδίο, ροή εργασίας ή πλαίσιο δημοσίευσης.

Μορφή αναγνωριστικού:

```text
OMI-PROFILE-NNN
```

Ένα προφίλ ΔΕΝ ΠΡΕΠΕΙ να έρχεται σιωπηρά σε αντίθεση με την προδιαγραφή που περιγράφει. Οποιαδήποτε σκόπιμη ασυμβατότητα απαιτεί ξεχωριστή έκδοση της προδιαγραφής ή μια επέκταση για την οποία δηλώνεται ρητά ότι δεν συμμορφώνεται.

### 5.3 Μητρώο

Ένα μητρώο ορίζει ελεγχόμενους αναγνωριστικούς κωδικούς, τιμές, τύπους μέσων, ρόλους, δυνατότητες ή σημεία επέκτασης.

Μορφή αναγνωριστικού:

```text
OMI-REG-NNN
```

Οι καταχωρήσεις στο μητρώο ΠΡΕΠΕΙ να διαθέτουν σταθερούς αναγνωριστικούς κωδικούς και τεκμηριωμένες καταστάσεις κύκλου ζωής.

### 5.4 Σχήμα

Ένα σχήμα είναι μια τυποποιημένη περιγραφή, αναγνώσιμη από μηχανή, ενός τμήματος του μοντέλου δεδομένων του «OMI».

Μορφή αναγνωριστικού:

```text
OMI-SCHEMA-NNN
```

Ένα έγγραφο σχήματος ΠΡΕΠΕΙ να αναφέρει ποια έκδοση προδιαγραφής κειμένου υλοποιεί.

### 5.5 Παράδειγμα

Ένα επίσημο παράδειγμα παρουσιάζει περιεχόμενο που συμμορφώνεται ή που σκόπιμα δεν συμμορφώνεται.

Μορφή αναγνωριστικού:

```text
OMI-EXAMPLE-NNN
```

Τα παραδείγματα ΠΡΕΠΕΙ να αναφέρουν αν είναι:

- κανονιστικό·
- ενημερωτικό·
- έγκυρο;
- μη έγκυρο;
- ελάχιστο·
- ολοκληρωμένη·
- συγκεκριμένο για κάθε προφίλ.

### 5.6 Έγγραφο διακυβέρνησης

Ένα έγγραφο διακυβέρνησης καθορίζει τη διαδικασία του έργου, τις αρμοδιότητες, τον κύκλο ζωής, τη διαχείριση των εκδόσεων, τις συντακτικές πρακτικές ή τους κανόνες συνεισφοράς.

Τα έγγραφα διακυβέρνησης δεν λαμβάνουν αναγνωριστικά τύπου «`OMI-SPEC`», εκτός εάν καθορίζουν άμεσα τη συμμόρφωση των υλοποιητών.

## 6. Συμβάσεις ονοματολογίας αρχείων και αναγνωριστικών

### 6.1 Ονόματα αρχείων

Markdown Τα ονόματα αρχείων ΠΡΕΠΕΙ να γράφονται με μικρά γράμματα και κεφαλαία ανά λέξη.

Σωστό:

```text
bibliographic-record-model.md
reference-library-architecture.md
specification-lifecycle.md
```

Λάθος:

```text
BibliographicRecordModel.md
reference_library.md
Reference Library.md
```

### 6.2 Μόνιμοι αναγνωριστικοί κωδικοί

Ένας μόνιμος αναγνωριστικός κωδικός εγγράφου ΔΕΝ ΠΡΕΠΕΙ να αλλάζει όταν:

- ο τίτλος αλλάζει·
- το αρχείο μετακινείται·
- οι αλλαγές στις κατηγορίες της πλευρικής στήλης·
- το έγγραφο έχει μεταφραστεί·
- κυκλοφορεί μια νέα δευτερεύουσα έκδοση ή έκδοση επιδιόρθωσης.

### 6.3 Επικεφαλίδες και σημεία αναφοράς

Το κείμενο των επικεφαλίδων ΠΡΕΠΕΙ να παραμένει σταθερό μετά τη δημοσίευση, καθώς οι δημιουργημένοι σύνδεσμοι ενδέχεται να χρησιμοποιηθούν εξωτερικά.

Όταν πρέπει να αλλάξει μια επικεφαλίδα, ο ιστότοπος ΘΑ ΠΡΕΠΕΙ να διατηρήσει μια ανακατεύθυνση ή έναν ρητό παλαιό σύνδεσμο, όπου αυτό υποστηρίζεται.

### 6.4 Ονόματα ιδιοτήτων

Τα ονόματα ιδιοτήτων που αναγνώζονται από μηχανή ΠΡΕΠΕΙ να χρησιμοποιούν μικρά γράμματα με «camel case», εκτός εάν κάποιο άλλο πρότυπο αντιστοίχισης απαιτεί διαφορετική σύμβαση.

Παραδείγματα:

```json
{
  "documentLanguage": "en",
  "bibliographicTargetId": "ref-001",
  "createdAt": "2026-08-06T16:00:00Z"
}
```

Οι ιδιότητες τύπου Boolean ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν καταφατικά ονόματα που περιγράφουν την κατάσταση «`true`».

Προτιμώμενο:

```text
isArchived
preserveUnknownProperties
requiresReview
```

Να αποφεύγετε:

```text
notArchived
noPreservation
skipNoReview
```

### 6.5 Τιμές απαρίθμησης

Οι τιμές της απαρίθμησης ΠΡΕΠΕΙ να γράφονται με μικρά γράμματα και κεφαλαία γράμματα ανά διαστήματα:

```text
journal-article
co-author
review-candidate
```

Μόλις δημοσιευθούν σε μια σταθερή προδιαγραφή, οι τιμές της απαρίθμησης ΔΕΝ ΠΡΕΠΕΙ να μετονομάζονται εντός της ίδιας κύριας έκδοσης.

## 7. Απαιτούμενα μεταδεδομένα εγγράφων

Κάθε προδιαγραφή ΠΡΕΠΕΙ να ξεκινά με μεταδεδομένα κατανοητά από τον άνθρωπο, τα οποία να περιέχουν τουλάχιστον:

| Πεδίο | Απαίτηση |
|---|---|
| Αναγνωριστικό | Μόνιμο αναγνωριστικό του OMI |
| Τίτλος | Επίσημος τίτλος |
| Έκδοση | Έκδοση εγγράφου |
| Κατάσταση | Στάδιο κύκλου ζωής |
| Τύπος εγγράφου | Κανονιστικό, ενημερωτικό ή μικτού τύπου |
| Συντάκτες | Υπεύθυνοι συντάκτες ή συντακτική ομάδα |
| Τελευταία ενημέρωση | Ημερομηνία κατά ISO 8601 |
| Αντικαθιστά | Προηγούμενο έγγραφο, όπου ισχύει |
| Αντικαταστάθηκε από | Διάδοχος, όπου ισχύει |
| Εξαρτάται από | Κανονιστικές εξαρτήσεις |
| Χρησιμοποιείται από | Γνωστές εξαρτώμενες προδιαγραφές |
| Κατάσταση υλοποίησης | Περίληψη ή σύνδεσμος προς τον πίνακα υλοποίησης |

Τα προλογικά στοιχεία του αρχείου `Docusaurus` ΠΡΕΠΕΙ να περιέχουν μόνο τα μεταδεδομένα δημοσίευσης που απαιτούνται από τον ιστότοπο, όπως ο τίτλος, η ετικέτα της πλευρικής στήλης και η σειρά εμφάνισης. Τα κανονιστικά μεταδεδομένα ΠΡΕΠΕΙ να παραμένουν ορατά στο σώμα του εμφανιζόμενου εγγράφου.

## 8. Δομή τυποποιημένων προδιαγραφών

Μια προδιαγραφή του τύπου «OMI» (Πρότυπο για το ) ΘΑ ΠΡΕΠΕΙ να ακολουθεί την παρακάτω δομή. Οι ενότητες ΜΠΟΡΟΥΝ να παραλειφθούν μόνο όταν δεν ισχύουν.

### 8.1 Περίληψη

Μια συνοπτική περιγραφή του τι ορίζει η προδιαγραφή και του λόγου για τον οποίο υπάρχει.

Η περίληψη ΔΕΝ ΠΡΕΠΕΙ να περιέχει κανονιστικές απαιτήσεις.

### 8.2 Καθεστώς του παρόντος εγγράφου

Σε αυτή την ενότητα αναφέρεται:

- κατάσταση κύκλου ζωής·
- προσδοκίες σταθερότητας·
- αν οι ισχυρισμοί σχετικά με την εφαρμογή είναι ορθοί·
- αν εξακολουθεί να είναι δυνατή μια ασυμβίβαστη αλλαγή·
- όπου συζητούνται τα θέματα και οι αναθεωρήσεις.

### 8.3 Συμμόρφωση

Σε αυτή την ενότητα ορίζονται:

- κατηγορίες συμμορφούμενων υλοποιήσεων·
- υποχρεωτικές δυνατότητες·
- προαιρετικές δυνατότητες·
- σχέσεις προφίλ·
- πώς ελέγχεται ή δηλώνεται η συμμόρφωση.

### 8.4 Πεδίο εφαρμογής

Στην ενότητα «Πεδίο εφαρμογής» καθορίζεται το αντικείμενο του εγγράφου.

Θα ΠΡΕΠΕΙ επίσης να περιλαμβάνει μια ρητή υποενότητα με τίτλο **«Εκτός πεδίου εφαρμογής»**, όπου ενδέχεται να προκύψει σύγχυση ως προς τα όρια.

### 8.5 Ορολογία

Το έγγραφο ΠΡΕΠΕΙ να ορίζει τους εξειδικευμένους όρους που δεν έχουν ήδη οριστεί στο κεντρικό έγγραφο ορολογίας του OMI.

Οι ορισμοί ΠΡΕΠΕΙ να είναι συνοπτικοί και να μην περιέχουν κυκλικές αναφορές.

### 8.6 Αρχές σχεδιασμού

Σε αυτή την ενημερωτική ενότητα εξηγούνται οι αρχιτεκτονικές αρχές που καθοδηγούν τις προδιαγραφές.

Οι αρχές σχεδιασμού ΔΕΝ ΠΡΕΠΕΙ να αντικαθιστούν τις επαληθεύσιμες κανονιστικές απαιτήσεις.

### 8.7 Μοντέλο δεδομένων ή μοντέλο επεξεργασίας

Στο κύριο τμήμα του μοντέλου περιγράφονται οι οντότητες, οι ιδιότητες, οι σχέσεις, οι καταστάσεις και η συμπεριφορά επεξεργασίας.

Η προδιαγραφή σε μορφή πεζού κειμένου εξακολουθεί να αποτελεί την έγκυρη πηγή, εκτός εάν το έγγραφο ορίζει ρητά ότι ένα μηχανικά αναγνώσιμο τεκμήριο αποτελεί την έγκυρη πηγή για ένα καθορισμένο υποσύνολο.

### 8.8 Επαλήθευση και διαχείριση σφαλμάτων

Το έγγραφο ΠΡΕΠΕΙ να ορίζει:

- μη έγκυρη εισαγωγή·
- μη υποστηριζόμενη εισαγωγή·
- προειδοποιήσεις·
- αποκαταστάσιμες και μη αποκαταστάσιμες αστοχίες·
- απαιτήσεις αναφοράς σφαλμάτων·
- συμπεριφορά διατήρησης.

### 8.9 Επεκτασιμότητα

Η προδιαγραφή ΘΑ ΠΡΕΠΕΙ να προσδιορίζει τα σημεία επέκτασης και να ορίζει τον τρόπο διαχείρισης των άγνωστων επεκτάσεων.

Οι επεκτάσεις ΔΕΝ ΠΡΕΠΕΙ να επαναπροσδιορίζουν τη σημασία των βασικών ιδιοτήτων.

### 8.10 Διαλειτουργικότητα

Σε αυτή την ενότητα περιγράφονται οι αντιστοιχίσεις με εξωτερικά πρότυπα και διακρίνονται:

- αναπαραστάσεις χωρίς απώλειες·
- αντιστοιχίσεις με περιορισμένη απώλεια·
- αντιστοιχίσεις με απώλειες·
- δομές που δεν υποστηρίζονται.

### 8.11 Θέματα ασφάλειας, προστασίας προσωπικών δεδομένων και ακεραιότητας

Κάθε κανονιστική προδιαγραφή ΠΡΕΠΕΙ να εξετάζει εάν ενέχει κινδύνους που σχετίζονται με:

- ενεργό περιεχόμενο;
- ανάκτηση εξωτερικών πηγών·
- παραποίηση αναγνωριστικού·
- μη αξιόπιστα μεταδεδομένα·
- προσωπικά στοιχεία·
- κρυφές σημειώσεις·
- έλεγχος πρόσβασης·
- ακεραιότητα της υπογραφής ή της προέλευσης·
- απόρριψη υπηρεσίας·
- μη ασφαλής απόδοση.

Η δήλωση ότι δεν είναι γνωστές συγκεκριμένες παράμετροι είναι αποδεκτή μόνο μετά από ρητή εξέταση.

### 8.12 Θέματα προσβασιμότητας

Οι προδιαγραφές που επηρεάζουν την παρουσίαση ή την αλληλεπίδραση με τον χρήστη ΘΑ ΠΡΕΠΕΙ να αναφέρουν τις απαιτήσεις προσβασιμότητας ή τις αναμενόμενες αντιστοιχίσεις.

### 8.13 Θέματα διεθνοποίησης

Οι προδιαγραφές που αφορούν κείμενο, ονόματα, ημερομηνίες, ταξινόμηση, αναγνωριστικά ή απεικόνιση ΠΡΕΠΕΙ να λαμβάνουν υπόψη:

- Unicode;
- ετικέτες γλώσσας;
- αμφίδρομο κείμενο·
- τοπικά ονόματα·
- παραλλαγή σεναρίου;
- μεταγραφή·
- τιμές μηχανής ανεξάρτητες από τη γλώσσα·
- ζώνες ώρας και απεικόνιση ημερολογίου.

### 8.14 Παραδείγματα

Τα παραδείγματα ΘΑ ΠΡΕΠΕΙ να εμφανίζονται κοντά στον κανόνα που επεξηγούν. Τα εκτενή και ολοκληρωμένα παραδείγματα ΘΑ ΠΡΕΠΕΙ να διατηρούνται ως ξεχωριστά, επικυρωμένα αρχεία και να παραπέμπονται από την προδιαγραφή.

### 8.15 Βιβλιογραφία

Οι αναφορές ΠΡΕΠΕΙ να χωριστούν σε:

- **Παραπομπές σε πρότυπα**: απαιτούνται για την εφαρμογή ή την ερμηνεία της προδιαγραφής·
- **Πληροφοριακές αναφορές**: γενικές πληροφορίες ή σχετικό υλικό.

### 8.16 Ιστορικό αλλαγών

Το ιστορικό εκδόσεων ΠΡΕΠΕΙ να συνοψίζει τις ουσιαστικές αλλαγές. Το ιστορικό του Git από μόνο του δεν αποτελεί επαρκή υποκατάστατο ενός δημοσιευμένου ιστορικού αλλαγών.

## 9. Κανόνες ορολογίας

### 9.1 Βασικοί ορισμοί

Οι όροι με διατομεακή σημασία ΠΡΕΠΕΙ να ορίζονται στο κεντρικό έγγραφο ορολογίας OMI.

Μια προδιαγραφή ΜΠΟΡΕΙ να περιορίσει την έννοια ενός όρου στο δικό της πεδίο εφαρμογής, αλλά ΔΕΝ ΠΡΕΠΕΙ να αποδίδει σιωπηρά μια αντικρουόμενη έννοια.

### 9.2 Προτιμώμενοι βασικοί όροι

Οι παρακάτω διακρίσεις ΠΡΕΠΕΙ να διατηρηθούν.

#### Χειρόγραφο

Ένα επιστημονικό έργο που παρουσιάζεται ως επεξεργάσιμο, δομημένο πνευματικό αντικείμενο καθ’ όλη τη διάρκεια του κύκλου ζωής του.

#### Έγγραφο

Μια συγκεκριμένη δομημένη αναπαράσταση ή ένα σύνολο περιεχομένου. Ένα χειρόγραφο μπορεί να έχει πολλαπλές αναπαραστάσεις ή εκδόσεις εγγράφων.

#### Επιστημονικό αντικείμενο

Μια αναγνωρίσιμη σημασιολογική οντότητα που βρίσκεται εντός ενός χειρογράφου ή συνδέεται με αυτό.

#### Βιβλιογραφική εγγραφή

Μια δομημένη περιγραφή μιας πηγής που έχει αναφερθεί ή μπορεί να αναφερθεί, ανεξάρτητα από συγκεκριμένη περίπτωση αναφοράς.

#### Βιβλιοθήκη αναφοράς

Η συλλογή βιβλιογραφικών εγγραφών σε επίπεδο χειρογράφου, οι οποίες έχουν επιλεγεί για πιθανή ή πραγματική αναφορά.

#### Εμφάνιση παραπομπής

Μια αναφορά από μια συγκεκριμένη θέση σε ένα χειρόγραφο σε μια καταχώριση της βιβλιοθήκης αναφορών, η οποία μπορεί προαιρετικά να περιλαμβάνει δείκτες θέσης, προθέματα, επιθήματα και σκοπό της παραπομπής.

#### Αναφορά σε μορφή κειμένου

Κείμενο παρουσίασης που δημιουργήθηκε με βάση μια αναφορά, μια βιβλιογραφική εγγραφή και ένα προφίλ απεικόνισης.

#### Αγκυροβόλιο

Μια σταθερή ή προσδιορίσιμη αναφορά σε μια θέση, ένα εύρος, ένα αντικείμενο ή μια κατάσταση εντός επιστημονικού περιεχομένου.

#### Σχόλιο

Ένα επιστημονικό αντικείμενο που συνδέει ένα σύνολο σχολίων ή δομημένων πληροφοριών με έναν ή περισσότερους στόχους.

#### Προφίλ

Ένα καθορισμένο σύνολο περιορισμών, προεπιλογών ή επεκτάσεων που εφαρμόζονται σε μία ή περισσότερες προδιαγραφές του «OMI» για συγκεκριμένο σκοπό.

### 9.3 Κεφαλαιοποίηση

Οι γενικές έννοιες γράφονται με μικρά γράμματα:

> ένα χειρόγραφο, μια αναφορά, ένα προφίλ

Στα επίσημα έγγραφα και στις ονομασίες των στοιχείων χρησιμοποιείται η γραφή με κεφαλαία αρχικά:

> Μοντέλο αναφοράς, Open Manuscript Studio, Μητρώο προδιαγραφών OMI

Τα ονόματα ιδιοτήτων και οι κυριολεκτικές τιμές ΠΡΕΠΕΙ να μορφοποιούνται ως κώδικας:

> Η ιδιότητα «`documentLanguage`» περιέχει μια ετικέτα γλώσσας BCP 47.

### 9.4 Συντομογραφίες

Μια συντομογραφία ΠΡΕΠΕΙ να αναπτυχθεί κατά την πρώτη ουσιαστική χρήση της, εκτός αν είναι ευρέως αναγνωρισμένη στο τεχνικό κοινό στο οποίο απευθύνεται το κείμενο.

Προτιμώμενο:

> Γλώσσα στυλ παραπομπών (CSL)

Σε μεταγενέστερες χρήσεις ΕΝΔΕΧΕΤΑΙ να χρησιμοποιηθεί το `CSL`.

Τα ακρωνύμια ΔΕΝ ΠΡΕΠΕΙ να μετατρέπονται σε πληθυντικό με απόστροφο.

Σωστό:

> DOIs, APIs, URL

## 10. Παρουσίαση του μοντέλου δεδομένων

### 10.1 Περιγραφές οντοτήτων

Κάθε οντότητα ΠΡΕΠΕΙ να ορίζει:

- σκοπός·
- αναγνωριστικό;
- κύκλος ζωής;
- απαιτούμενες ιδιότητες·
- προαιρετικές ιδιότητες·
- σχέσεις·
- αμετάβλητα·
- σημεία επέκτασης.

### 10.2 Πίνακες ιδιοτήτων

Οι πίνακες ιδιοτήτων ΠΡΕΠΕΙ να ακολουθούν την εξής σειρά:

| Ιδιότητα | Τύπος | Απαιτείται | Καρδινάλτητα | Περιγραφή |
|---|---|---:|---:|---|

Επιπλέον στήλες ΜΠΟΡΟΥΝ να περιλαμβάνουν:

- προεπιλογή;
- περιορισμοί·
- πηγή;
- ταξινόμηση απορρήτου·
- παρουσίαση της έκδοσης.

### 10.3 Καρδινάλια

Η καρδινάλια ΠΡΕΠΕΙ να εκφράζεται με συνέπεια:

- `0..1` — προαιρετική μεμονωμένη τιμή·
- `1` — ακριβώς μία τιμή·
- `0..*` — μηδέν ή περισσότερες τιμές·
- `1..*` — μία ή περισσότερες τιμές.

### 10.4 Μηδενικές, ελλείπουσες και κενές τιμές

Μια προδιαγραφή ΠΡΕΠΕΙ, όπου αυτό είναι σχετικό, να διακρίνει μεταξύ:

- μια ιδιότητα που λείπει·
- μια ιδιότητα με `null`;
- μια κενή συμβολοσειρά·
- ένας κενός πίνακας·
- μια άγνωστη τιμή·
- μια τιμή που παραλείπεται σκόπιμα·
- μια τιμή που δεν ισχύει.

Αυτές οι καταστάσεις ΔΕΝ ΠΡΕΠΕΙ να θεωρούνται ισοδύναμες, εκτός αν αυτό αναφέρεται ρητά στις προδιαγραφές.

### 10.5 Ημερομηνίες και ώρες

Οι ημερομηνίες και οι ώρες που μπορούν να αναγνωστούν από μηχανή ΠΡΕΠΕΙ να χρησιμοποιούν μορφές συμβατές με το πρότυπο ISO 8601, όπως ορίζονται από το σχετικό σχήμα.

Μια χρονική στιγμή ΠΡΕΠΕΙ να περιλαμβάνει μια διαφορά ώρας ως προς το UTC. Οι τιμές UTC ΠΡΕΠΕΙ να χρησιμοποιούν το πρότυπο «`Z`».

Παράδειγμα:

```text
2026-08-06T16:10:15Z
```

Μια ημερομηνία χωρίς ώρα ΔΕΝ ΠΡΕΠΕΙ να ερμηνεύεται σιωπηρά ως μια συγκεκριμένη στιγμή.

### 10.6 Ετικέτες γλώσσας

Η αναγνώριση γλώσσας με μηχανική ανάγνωση ΠΡΕΠΕΙ να χρησιμοποιεί ετικέτες γλώσσας BCP 47, εκτός εάν κάποιο πρότυπο αντιστοίχισης επιβάλλει διαφορετική αναπαράσταση.

Παραδείγματα:

```text
en
hu
de
zh-Hant
sr-Latn
```

## 11. Παραδείγματα και αποσπάσματα κώδικα

### 11.1 Ισχύς

Τα παραδείγματα κώδικα που ισχυρίζονται ότι συμμορφώνονται ΠΡΕΠΕΙ να είναι συντακτικά έγκυρα και ΘΑ ΠΡΕΠΕΙ να επαληθεύονται αυτόματα.

Τα αποσπασματικά παραδείγματα ΠΡΕΠΕΙ να περιέχουν μια ορατή ένδειξη, όπως ένα σχόλιο ή τρεις τελείες, και ΔΕΝ ΠΡΕΠΕΙ να παρουσιάζονται ως πλήρη και έγκυρα έγγραφα.

### 11.2 JSON

JSON Τα παραδείγματα ΠΡΕΠΕΙ:

- χρησιμοποιήστε διπλά εισαγωγικά·
- χρησιμοποιήστε εσοχή δύο διαστημάτων·
- αποφύγετε τα σχόλια σε μπλοκ με την ένδειξη «`json`»·
- να χρησιμοποιείτε σταθερούς αναγνωριστικούς παραδειγμάτων·
- να αποφεύγετε τα πραγματικά προσωπικά δεδομένα·
- Χρησιμοποιήστε έγκυρο Unicode.

Παράδειγμα:

```json
{
  "id": "citation-001",
  "targetId": "reference-001",
  "locator": {
    "type": "page",
    "value": "24–31"
  }
}
```

### 11.3 XML

XML Τα παραδείγματα ΠΡΕΠΕΙ να δηλώνουν χώρους ονομάτων όταν η σημασιολογία των χώρων ονομάτων έχει σημασία. Τα προθέματα που χρησιμοποιούνται στα παραδείγματα ΘΑ ΠΡΕΠΕΙ να παραμένουν συνεπή σε ολόκληρη τη σειρά προδιαγραφών.

### 11.4 Διευθύνσεις URL και αναγνωριστικά

Στα παραδείγματα ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούνται, όπου είναι δυνατόν, τιμές που έχουν δεσμευτεί ή είναι σαφώς φανταστικές.

Μην χρησιμοποιείτε αναγνωριστικά που θα μπορούσαν να εκληφθούν ως πραγματικά ακαδημαϊκά αναγνωριστικά, εκτός εάν το παράδειγμα παραπέμπει ρητά σε ένα πραγματικό έργο και η παραπομπή είναι ακριβής.

### 11.5 Θετικά και αρνητικά παραδείγματα

Οι προδιαγραφές ΠΡΕΠΕΙ να περιλαμβάνουν:

- τουλάχιστον ένα ελάχιστο έγκυρο παράδειγμα·
- τουλάχιστον ένα αντιπροσωπευτικό έγκυρο παράδειγμα·
- μη έγκυρα παραδείγματα για σημαντικούς κανόνες επικύρωσης·
- παραδείγματα μετεγκατάστασης κατά την αλλαγή της υπάρχουσας συμπεριφοράς.

Τα μη έγκυρα παραδείγματα ΠΡΕΠΕΙ να αναφέρουν τον λόγο για τον οποίο δεν είναι έγκυρα.

### 11.6 Παραδείγματα ετικετών

Τα παραδείγματα ΠΡΕΠΕΙ να φέρουν επισήμανση και παραπομπές με συνέπεια:

```text
Example 1 — Minimal citation occurrence
Example 2 — Citation with a page locator
Example 3 — Invalid unresolved target
```

## 12. Σχήματα και διαγράμματα

### 12.1 Σκοπός

Ένα διάγραμμα ΠΡΕΠΕΙ να αποσαφηνίζει τις σχέσεις, τις μεταβάσεις κατάστασης, την αρχιτεκτονική ή τη διαδικασία επεξεργασίας, οι οποίες θα ήταν δύσκολο να κατανοηθούν μόνο από το κείμενο.

Ένα διάγραμμα ΔΕΝ ΠΡΕΠΕΙ να αποτελεί τη μοναδική κανονιστική αναπαράσταση μιας απαίτησης.

### 12.2 Προσβασιμότητα

Κάθε ουσιαστικό στοιχείο ΠΡΕΠΕΙ να περιλαμβάνει:

- εναλλακτικό κείμενο;
- μια λεζάντα·
- μια αντίστοιχη εξήγηση σε πεζό λόγο.

Οι πληροφορίες ΔΕΝ ΠΡΕΠΕΙ να βασίζονται αποκλειστικά στο χρώμα.

### 12.3 Πηγή του διαγράμματος

Ο επεξεργάσιμος πηγαίος κώδικας για σημαντικά διαγράμματα ΘΑ ΠΡΕΠΕΙ να αποθηκεύεται στο αποθετήριο μαζί με τα εξαγόμενα αρχεία.

### 12.4 Σημειογραφία

Μια προδιαγραφή ΠΡΕΠΕΙ να εξηγεί τη μη προφανή σημειογραφία. Τα διαγράμματα τύπου UML ΔΕΝ ΠΡΕΠΕΙ να υπονοούν τυπική σημασιολογία UML, εκτός εάν το έγγραφο τα υιοθετεί ρητά.

## 13. Πίνακες και καταλόγους

Οι πίνακες ΠΡΕΠΕΙ να χρησιμοποιούνται για δομημένες συγκρίσεις και όχι ως υποκατάστατο εκτενών παραγράφων.

Ένας πίνακας ΠΡΕΠΕΙ να έχει σαφείς επικεφαλίδες στηλών. Τα κελιά ΘΑ ΠΡΕΠΕΙ να περιέχουν συνοπτικές τιμές.

Οι λίστες με κουκκίδες είναι κατάλληλες για σύνολα χωρίς συγκεκριμένη σειρά. Οι αριθμημένες λίστες ΠΡΕΠΕΙ να χρησιμοποιούνται μόνο όταν η σειρά ή η ακολουθία βημάτων έχει σημασία.

Οι ένθετες λίστες ΠΡΕΠΕΙ να περιορίζονται, ώστε να διατηρείται η αναγνωσιμότητα και η ποιότητα της μετάφρασης.

## 14. Παραπομπές

### 14.1 Εσωτερικές παραπομπές

Οι κανονιστικές αναφορές σε άλλο έγγραφο του Οργανισμού Τυποποίησης της Αμερικής (OMI) ΠΡΕΠΕΙ να χρησιμοποιούν τον μόνιμο αναγνωριστικό κωδικό του και ΘΑ ΠΡΕΠΕΙ να περιλαμβάνουν τον τίτλο του.

Προτιμώμενο:

> Βλ. OMI-SPEC-006, *Μοντέλο βιβλιογραφικής εγγραφής*.

Ένας σχετικός σύνδεσμος Markdown ΜΠΟΡΕΙ να συνοδεύει τον αναγνωριστικό στην πηγή.

### 14.2 Παραπομπές σε ενότητες

Οι παραπομπές ΠΡΕΠΕΙ να αναφέρουν τον τίτλο της ενότητας αντί να βασίζονται αποκλειστικά στον αριθμό της ενότητας, καθώς οι αριθμοί ενδέχεται να αλλάξουν κατά τη διάρκεια της σύνταξης.

Προτιμώμενο:

> Δείτε την ενότητα «Κανονικοποίηση αναγνωριστικών» του εγγράφου OMI-SPEC-006.

### 14.3 Εξωτερικές αναφορές

Οι εξωτερικές κανονιστικές αναφορές ΠΡΕΠΕΙ να παραπέμπουν σε σταθερές και έγκυρες πηγές. Μια προδιαγραφή ΠΡΕΠΕΙ να προσδιορίζει την έκδοση ή την έκδοση στην οποία γίνεται αναφορά, όταν η ερμηνεία μπορεί να διαφέρει μεταξύ των εκδόσεων.

### 14.4 Ανθεκτικότητα των συνδέσεων

Τα έγγραφα ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν κατά προτίμηση μόνιμους αναγνωριστικούς και κανονικές διευθύνσεις URL τεκμηρίωσης αντί για προσωρινές σελίδες έργου.

## 15. Ευθυγράμμιση σχήματος και πεζού κειμένου

### 15.1 Αρμοδιότητα

Κάθε προδιαγραφή που βασίζεται σε σχήμα ΠΡΕΠΕΙ να αναφέρει τη σχέση ισχύος μεταξύ του κειμένου και του σχήματος.

Συνιστώμενος κανόνας:

- η πρόζα καθορίζει τη σημασιολογία και τη συμπεριφορά επεξεργασίας·
- το σχήμα ορίζει δομικούς περιορισμούς που μπορούν να ελεγχθούν από υπολογιστή·
- μια ασυμφωνία είναι ένα ελάττωμα προδιαγραφών που ΠΡΕΠΕΙ να διορθωθεί·
- Οι υλοποιήσεις ΔΕΝ ΠΡΕΠΕΙ να επινοούν σημασιολογία αποκλειστικά με βάση τους μηχανισμούς του σχήματος.

### 15.2 Περιγραφές σχημάτων

Οι περιγραφές των ιδιοτήτων του σχήματος ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν την ίδια ορολογία με την προδιαγραφή σε μορφή κειμένου και ΘΑ ΠΡΕΠΕΙ να περιλαμβάνουν παραπομπή στη σχετική απαίτηση ή ενότητα, όπου αυτό επιτρέπεται από τα εργαλεία.

### 15.3 Περιπτώσεις αθέτησης υποχρεώσεων

Μια προεπιλεγμένη τιμή σχήματος ΔΕΝ ΠΡΕΠΕΙ να θεωρείται ως εντολή εισαγωγής μιας τιμής, εκτός εάν η περιγραφή του κειμένου ορίζει ρητά αυτή τη συμπεριφορά επεξεργασίας.

### 15.4 Πρόσθετες ιδιότητες

Οι προδιαγραφές ΠΡΕΠΕΙ να καθορίζουν ρητά εάν οι άγνωστες ιδιότητες είναι:

- απορρίφθηκε·
- αγνοήθηκε·
- διατηρημένος·
- υπόκεινται σε επεκτάσεις·
- επιτρέπεται μόνο σε δηλωμένους χώρους ονομάτων.

## 16. Σύνταξη εγγράφων συμμόρφωσης

### 16.1 Κατηγορίες συμμόρφωσης

Μια προδιαγραφή ΘΑ ΠΡΕΠΕΙ να ορίζει ονομασμένες κατηγορίες συμμόρφωσης, όταν δεν εκτελεί κάθε υλοποίηση τον ίδιο ρόλο.

Παραδείγματα:

- συμμορφούμενος παραγωγός·
- συμμορφούμενος καταναλωτής·
- εργαλείο επαλήθευσης συμμόρφωσης·
- συμβατός μηχανισμός απόδοσης·
- συμβατός επεξεργαστής;
- επεξεργαστής διατήρησης σύμφωνα με τις προδιαγραφές.

### 16.2 Παρατηρήσιμη συμπεριφορά

Οι απαιτήσεις συμμόρφωσης ΠΡΕΠΕΙ να βασίζονται σε παρατηρήσιμα στοιχεία εισόδου, εξόδου, κατάστασης ή τεκμηριωμένης ικανότητας.

Αποφύγετε τις απαιτήσεις που αφορούν την εσωτερική αρχιτεκτονική, εκτός εάν η εν λόγω αρχιτεκτονική είναι απαραίτητη για τη διαλειτουργικότητα ή την ασφάλεια.

Κακό:

> Οι υλοποιήσεις ΠΡΕΠΕΙ να χρησιμοποιούν σχεσιακή βάση δεδομένων.

Καλύτερα:

> Οι υλοποιήσεις ΠΡΕΠΕΙ να διατηρούν σταθερούς τους αναγνωριστικούς των αντικειμένων κατά τη διάρκεια των λειτουργιών αποθήκευσης και επαναφόρτωσης.

### 16.3 Προαιρετικές λειτουργίες

Μια προαιρετική λειτουργία ΜΠΟΡΕΙ να παραλειφθεί. Εάν υλοποιηθεί, ΠΡΕΠΕΙ να πληροί όλες τις απαιτήσεις που έχουν οριστεί για τη συγκεκριμένη λειτουργία.

### 16.4 Δηλώσεις συμμόρφωσης

Μια δήλωση συμμόρφωσης ΘΑ ΠΡΕΠΕΙ να περιλαμβάνει:

- όνομα και έκδοση της εφαρμογής·
- αναγνωριστικό προδιαγραφής και ακριβής έκδοση·
- υποστηριζόμενη κατηγορία συμμόρφωσης·
- υποστηριζόμενα προφίλ·
- γνωστοί περιορισμοί·
- έκδοση της σουίτας δοκιμών, όπου είναι διαθέσιμη.

## 17. Ορολογία σφαλμάτων και προειδοποιήσεων

OMI Τα έγγραφα ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν αυτούς τους όρους με συνέπεια.

### Σφάλμα

Μια κατάσταση που παραβιάζει μια κανονιστική απαίτηση ή εμποδίζει την ορθή ολοκλήρωση της ζητούμενης λειτουργίας.

### Προειδοποίηση

Μια κατάσταση που επιτρέπεται ή μπορεί να αποκατασταθεί, αλλά ενδέχεται να προκαλέσει απώλεια πληροφοριών, μειωμένη διαλειτουργικότητα ή απροσδόκητα αποτελέσματα.

### Λειτουργία που δεν υποστηρίζεται

Μια αναγνωρισμένη λειτουργία που δεν παρέχει η συγκεκριμένη υλοποίηση.

### Άγνωστη λειτουργία

Μια λειτουργία ή επέκταση που η εφαρμογή δεν αναγνωρίζει.

### Μη έγκυρη τιμή

Μια τιμή που παραβιάζει περιορισμούς σύνταξης, τύπου, εύρους, καρδινάλιας ή σημασιολογικούς περιορισμούς.

### Ανεπίλυτη αναφορά

Μια αναφορά της οποίας ο στόχος δεν μπορεί να προσδιοριστεί ή να προσπελαστεί στο τρέχον πλαίσιο επεξεργασίας.

Οι προδιαγραφές ΘΑ ΠΡΕΠΕΙ να αναφέρουν αν κάθε κατάσταση απαιτεί απόρριψη, αποκατάσταση, διατήρηση ή ειδοποίηση του χρήστη.

## 18. Αντιστοιχίσεις διαλειτουργικότητας

Ένα έγγραφο χαρτογράφησης ΠΡΕΠΕΙ να διακρίνει:

- πρότυπο πηγής;
- μοντέλο-στόχος·
- κατεύθυνση χαρτογράφησης;
- χαρτογράφηση προϋποθέσεων·
- διατηρημένες πληροφορίες·
- μετασχηματισμένες πληροφορίες·
- παραλειπόμενες πληροφορίες·
- πληροφορίες που παράγονται·
- ασάφεια·
- αναστρεψιμότητα.

Οι πίνακες αντιστοίχισης ΘΑ ΠΡΕΠΕΙ να χρησιμοποιούν ρητά αποτελέσματα, όπως:

```text
lossless
conditionally lossless
lossy
unsupported
implementation-defined
```

Η λέξη «συμβατός» ΔΕΝ ΠΡΕΠΕΙ να χρησιμοποιείται χωρίς να αναφέρεται η διάσταση συμβατότητας.

## 19. Σημειώσεις σχετικά με την κατάργηση και την αντικατάσταση

Μια λειτουργία που έχει καταργηθεί παραμένει ορισμένη, αλλά δεν συνιστάται πλέον για νέο περιεχόμενο ή υλοποιήσεις.

Οι ειδοποιήσεις κατάργησης ΠΡΕΠΕΙ να αναφέρουν:

- η λειτουργία που έχει καταργηθεί·
- η έκδοση στην οποία καταργήθηκε η χρήση της·
- ο λόγος·
- το ανταλλακτικό, όταν είναι διαθέσιμο·
- οδηγίες για τη μετανάστευση·
- η παλαιότερη έκδοση στην οποία ενδέχεται να πραγματοποιηθεί η διαγραφή.

Ένα έγγραφο που έχει αντικατασταθεί ΠΡΕΠΕΙ να παραμείνει διαθέσιμο και ΠΡΕΠΕΙ να αναφέρει το έγγραφο που το αντικαθιστά.

Το κανονιστικό κείμενο ΔΕΝ ΠΡΕΠΕΙ να αφαιρείται σιωπηρά από τις δημοσιευμένες σταθερές εκδόσεις.

## 20. Ταξινόμηση των συντακτικών αλλαγών

Κάθε αίτημα ενημέρωσης (pull request) που αφορά μια προδιαγραφή ΠΡΕΠΕΙ να ταξινομεί τις αλλαγές σε μία ή περισσότερες από τις ακόλουθες κατηγορίες:

- διευκρίνιση της σύνταξης·
- κανονιστική διευκρίνιση·
- συμβατή κανονιστική προσθήκη·
- ασυμβίβαστη κανονιστική αλλαγή·
- διόρθωση παραδείγματος·
- διόρθωση σχήματος·
- διόρθωση ασφαλείας·
- ενημέρωση μετάφρασης·
- απόσυρση·
- αντικατάσταση.

Η ταξινόμηση ΠΡΕΠΕΙ να είναι σύμφωνη με την Πολιτική Διαχείρισης Εκδόσεων της Υπηρεσίας Διαχείρισης Περιεχομένου (OMI).

## 21. Οδηγίες μετάφρασης

### 21.1 Κανονιστική πηγή

Εκτός αν ορίζεται ρητά διαφορετικά, η αγγλική έκδοση αποτελεί το κανονιστικό κείμενο, ενώ οι μεταφράσεις έχουν ενημερωτικό χαρακτήρα.

### 21.2 Σύνδεση πηγαίου κώδικα με έκδοση

Κάθε επίσημη μετάφραση ΠΡΕΠΕΙ να αναφέρει:

- αναγνωριστικό του αρχικού εγγράφου·
- ακριβής έκδοση πηγής·
- έκδοση μετάφρασης;
- κατάσταση μετάφρασης;
- ημερομηνία τελευταίου συγχρονισμού.

### 21.3 Μη μεταφράσιμα διακριτικά

Τα παρακάτω ΠΡΕΠΕΙ να παραμείνουν αμετάβλητα, εκτός εάν μια προδιαγραφή ορίζει μια τοπικοποιημένη ετικέτα εμφάνισης:

- ονόματα ιδιοτήτων;
- τιμές απαρίθμησης·
- αναγνωριστικά απαιτήσεων·
- αναγνωριστικά σχημάτων·
- τύποι μέσων·
- URI χώρων ονομάτων;
- κώδικας;
- λεκτικά διακριτικά πρωτοκόλλου.

### 21.4 Συνέπεια στην ορολογία

Οι επίσημες μεταφράσεις ΠΡΕΠΕΙ να χρησιμοποιούν εγκεκριμένο γλωσσικό λεξιλόγιο. Οι μεταφραστές ΘΑ ΠΡΕΠΕΙ να διατηρούν τις εννοιολογικές διακρίσεις, ακόμη και όταν η καθημερινή γλώσσα τείνει να τις συγχέει.

### 21.5 Λέξεις-κλειδιά κανονιστικού χαρακτήρα

Οι κεφαλαίες κανονιστικές λέξεις-κλειδιά ΠΡΕΠΕΙ να παραμένουν στα αγγλικά στις επίσημες μεταφράσεις, συνοδευόμενες από μεταφρασμένη εξήγηση όπου αυτό κρίνεται σκόπιμο. Με αυτόν τον τρόπο αποφεύγεται η ασάφεια στη νομική ή τεχνική ερμηνεία.

## 22. Επεξεργασία με τη βοήθεια τεχνητής νοημοσύνης

Τα εργαλεία που υποστηρίζονται από τεχνητή νοημοσύνη ΜΠΟΡΟΥΝ να χρησιμοποιηθούν για την υποστήριξη της σύνταξης, της επιμέλειας, της μετάφρασης, της ελέγχου της ορολογίας, της δημιουργίας παραδειγμάτων ή του ελέγχου της συνέπειας.

### 22.1 Η ευθύνη του ανθρώπου

Κάθε δημοσιευμένο έγγραφο του «OMI» ΠΡΕΠΕΙ να έχει έναν υπεύθυνο επιμέλειας ή μια ομάδα επιμέλειας που να είναι υπεύθυνη για:

- ακρίβεια των γεγονότων·
- κανονιστική ορθότητα·
- συμμόρφωση με τις ισχύουσες προδιαγραφές·
- συμμόρφωση με τη νομοθεσία περί πνευματικής ιδιοκτησίας·
- αξιολόγηση της ασφάλειας και της προστασίας των προσωπικών δεδομένων·
- τελική έγκριση.

Τα αποτελέσματα της τεχνητής νοημοσύνης ΔΕΝ ΠΡΕΠΕΙ να θεωρούνται αξιόπιστα απλώς και μόνο επειδή είναι εύγλωττα ή διατυπωμένα με τεχνικό ύφος.

### 22.2 Επαλήθευση

Το περιεχόμενο που έχει δημιουργηθεί με τη βοήθεια τεχνητής νοημοσύνης ΠΡΕΠΕΙ να ελέγχεται ως προς τα εξής:

- το σύνολο προδιαγραφών πηγής·
- αξιόπιστα εξωτερικά πρότυπα·
- σχήματα και παραδείγματα·
- τη συμπεριφορά κατά την εφαρμογή, όπου αυτό έχει σημασία·
- ορολογία του έργου.

Οι παραγόμενες αναφορές, οι αναγνωριστικοί κωδικοί, τα αποσπάσματα και οι εξωτερικές παραπομπές ΠΡΕΠΕΙ να επαληθεύονται ανεξάρτητα πριν από τη δημοσίευση.

### 22.3 Αλλαγές στις προδιαγραφές

Μια πρόταση που έχει εκπονηθεί με τη βοήθεια τεχνητής νοημοσύνης και η οποία μεταβάλλει την κανονιστική συμπεριφορά ΠΡΕΠΕΙ να υπόκειται στις ίδιες απαιτήσεις όσον αφορά τον κύκλο ζωής, την αξιολόγηση, τις δοκιμές και τη διαχείριση εκδόσεων, όπως και κάθε πρόταση που έχει συνταχθεί από άνθρωπο.

Κανένας κανονιστικός κανόνας ΔΕΝ ΜΠΟΡΕΙ να γίνει αποδεκτός αποκλειστικά βάσει μιας σύστασης της τεχνητής νοημοσύνης.

### 22.4 Ευαίσθητο υλικό

Οι συντάκτες ΔΕΝ ΠΡΕΠΕΙ να υποβάλλουν εμπιστευτικά χειρόγραφα, προσωπικά δεδομένα, υλικό αξιολόγησης υπό απαγόρευση δημοσίευσης, διαπιστευτήρια, ιδιωτικά κλειδιά ή μη δημόσιες πληροφορίες ασφαλείας σε μια υπηρεσία τεχνητής νοημοσύνης, εκτός εάν η υπηρεσία και το πλαίσιο επεξεργασίας έχουν ρητά εξουσιοδοτηθεί για τις συγκεκριμένες πληροφορίες.

### 22.5 Προέλευση

Το έργο ΜΠΟΡΕΙ να καταγράφει σημαντική υποστήριξη από τεχνητή νοημοσύνη στις σημειώσεις συνεισφοράς, στις περιγραφές των αιτημάτων ενοποίησης ή στα συντακτικά μεταδεδομένα. Η εν λόγω αναφορά ΠΡΕΠΕΙ να περιγράφει τον ρόλο του εργαλείου, αντί να του αποδίδει την πατρότητα ή την ευθύνη.

Παράδειγμα:

> Έλεγχος γλώσσας και συνοχής με τη βοήθεια τεχνητής νοημοσύνης· όλο το κανονιστικό περιεχόμενο έχει επαληθευτεί και εγκριθεί από τον αναφερόμενο συντάκτη.

Η παροχή μικρής βοήθειας σε θέματα ορθογραφίας, γραμματικής, αναζήτησης ή μορφοποίησης δεν απαιτεί γνωστοποίηση σε επίπεδο εγγράφου, εκτός εάν αυτό απαιτείται από την πολιτική του έργου ή τους ισχύοντες κανόνες.

### 22.6 Μετάφραση

Οι μεταφράσεις που παράγονται από μηχανή ΠΡΕΠΕΙ να αντιμετωπίζονται ως προσχέδια έως ότου ελεγχθούν από έναν εξειδικευμένο μεταφραστή ή έναν ειδικό στον συγκεκριμένο τομέα.

Μια αυτόματη μετάφραση ΔΕΝ ΠΡΕΠΕΙ να χαρακτηριστεί ως επίσημη μετάφραση του OMI χωρίς ανθρώπινη επιμέλεια και επαλήθευση της πρωτότυπης έκδοσης.

## 23. Πρακτικές σχετικά με τα αποθετήρια και τα αιτήματα ενσωμάτωσης

### 23.1 Μια συνολική ανησυχία

Ένα αίτημα αλλαγής προδιαγραφών ΠΡΕΠΕΙ να αφορά ένα ενιαίο αρχιτεκτονικό ή συντακτικό ζήτημα. Οι άσχετες αναδιαρθρώσεις ΠΡΕΠΕΙ να διαχωρίζονται, όπου αυτό είναι εφικτό.

### 23.2 Περιγραφή του αιτήματος ενσωμάτωσης

Ένα αίτημα ενσωμάτωσης ΠΡΕΠΕΙ να περιλαμβάνει:

- τι άλλαξε;
- γιατί άλλαξε·
- αν η συμπεριφορά είναι κανονική·
- επιπτώσεις στη συμβατότητα·
- τις σχετικές προδιαγραφές και τα σχήματα·
- πραγματοποιήθηκε έλεγχος εγκυρότητας·
- ερωτήματα που παραμένουν αναπάντητα.

### 23.3 Διαφορές που υπόκεινται σε έλεγχο

Οι εκτεταμένες μηχανικές αλλαγές στη μορφοποίηση ΠΡΕΠΕΙ να διαχωρίζονται από τις ουσιαστικές αλλαγές στο περιεχόμενο, ώστε οι κριτές να μπορούν να εντοπίσουν τις διαφορές στη συμπεριφορά.

### 23.4 Αρχεία που δημιουργήθηκαν

Τα δημιουργηθέντα αρχεία ΠΡΕΠΕΙ να αναφέρουν την πηγή τους και την εντολή δημιουργίας τους. Τα δημιουργηθέντα αρχεία ΔΕΝ ΠΡΕΠΕΙ να τροποποιούνται χειροκίνητα, εκτός εάν η ροή εργασίας το επιτρέπει ρητά.

### 23.5 Επαλήθευση

Πριν από τη συγχώνευση, οι σχετικοί έλεγχοι ΠΡΕΠΕΙ να περιλαμβάνουν:

- Markdown δημιουργία;
- έλεγχος εγκυρότητας εσωτερικών συνδέσμων·
- JSON και έλεγχος σύνταξης του XML·
- επικύρωση σχήματος;
- παραδείγματα τεστ·
- έλεγχοι ορολογίας·
- έλεγχοι για διπλά αναγνωριστικά·
- έλεγχοι κλειδιών μετάφρασης.

## 24. Προσβασιμότητα και αναγνωσιμότητα

OMI Οι προδιαγραφές ΠΡΕΠΕΙ να είναι προσβάσιμες από αναγνώστες με διαφορετικές συσκευές και ανάγκες πρόσβασης.

Οι συγγραφείς ΠΡΕΠΕΙ:

- να χρησιμοποιείτε μια λογική ιεραρχία επικεφαλίδων·
- να παρέχετε περιγραφικό κείμενο συνδέσμου·
- να παρέχετε εναλλακτικό κείμενο για εικόνες με ουσιαστικό περιεχόμενο·
- αποφύγετε να μεταδίδετε νόημα μόνο μέσω του χρώματος·
- να προσδιορίζουν τη γλώσσα των αποσπασμάτων που δεν είναι στα αγγλικά, όπου το εργαλείο το υποστηρίζει·
- αποφύγετε τους περιττά ευρείς πίνακες·
- να εξηγήσει τα σύμβολα και τις συντομογραφίες·
- Φροντίστε οι παράγραφοι να παραμένουν στο θέμα.

Η τεχνική ακρίβεια έχει προτεραιότητα έναντι των αυθαίρετων δεικτών αναγνωσιμότητας, αλλά οι περιττά περίπλοκες προτάσεις ΠΡΕΠΕΙ να αναδιατυπωθούν.

## 25. Κατάλογος ελέγχου ποιότητας

Πριν ένα έγγραφο προχωρήσει στο στάδιο **Υπό εξέταση**, οι συντάκτες ΠΡΕΠΕΙ να επιβεβαιώσουν όλα τα παρακάτω στοιχεία που ισχύουν.

### 25.1 Ταυτότητα και πεδίο εφαρμογής

- [ ] Το έγγραφο διαθέτει σταθερό αναγνωριστικό.
- [ ] Αναφέρονται η έκδοση και η κατάσταση του κύκλου ζωής.
- [ ] Τα όρια του πεδίου εφαρμογής και αυτά που δεν εμπίπτουν σε αυτό είναι σαφή.
- [ ] Παρατίθενται οι εξαρτήσεις και οι σχετικές προδιαγραφές.

### 25.2 Ορολογία

- [ ] Οι όροι αντιστοιχούν στην κεντρική ορολογία του OMI.
- [ ] Ορίζονται νέοι όροι.
- [ ] Οι παρόμοιες έννοιες διακρίνονται με συνέπεια.
- [ ] Τα ονόματα ιδιοτήτων και οι κυριολεκτικές τιμές ακολουθούν τη μορφοποίηση κώδικα.

### 25.3 Ποιότητα σύμφωνα με τα πρότυπα

- [ ] Οι κανονιστικές λέξεις-κλειδιά χρησιμοποιούνται σκόπιμα.
- [ ] Οι απαιτήσεις μπορούν να ελεγχθούν ανεξάρτητα.
- [ ] Όπου απαιτείται, αποδίδονται αναγνωριστικά απαιτήσεων.
- [ ] Η προαιρετική συμπεριφορά είναι ρητή.
- [ ] Έχει οριστεί η διαχείριση σφαλμάτων.
- [ ] Οι κατηγορίες συμμόρφωσης ορίζονται όπου απαιτείται.

### 25.4 Μοντέλα και παραδείγματα

- [ ] Οι οντότητες, οι σχέσεις και οι καρδινάλιες είναι ρητά καθορισμένες.
- [ ] Διακρίνονται οι καταστάσεις «λείπει», «μηδενική», «κενή» και «άγνωστη».
- [ ] Τα παραδείγματα είναι συντακτικά ορθά.
- [ ] Παρουσιάζονται σημαντικές περιπτώσεις μη έγκυρων αποτελεσμάτων.
- [ ] Τα παραδείγματα δεν περιέχουν προσωπικά ή εμπιστευτικά δεδομένα.

### 25.5 Διαλειτουργικότητα

- [ ] Οι εξωτερικές αντιστοιχίσεις υποδεικνύουν την κατεύθυνση και την απώλεια πληροφοριών.
- [ ] Έχει οριστεί ο τρόπος χειρισμού άγνωστων επεκτάσεων.
- [ ] Τεκμηριώνονται οι επιπτώσεις της έκδοσης και της μετάβασης.
- [ ] Το σχήμα και το κείμενο είναι ευθυγραμμισμένα.

### 25.6 Αξιολόγηση κινδύνων

- [ ] Έχουν εξεταστεί τα θέματα ασφάλειας.
- [ ] Έχουν εξεταστεί οι επιπτώσεις όσον αφορά την προστασία των προσωπικών δεδομένων και την προέλευση των δεδομένων.
- [ ] Έχουν ληφθεί υπόψη ζητήματα προσβασιμότητας.
- [ ] Εξετάζονται ζητήματα διεθνοποίησης.

### 25.7 Δημοσίευση

- [ ] Οι εσωτερικοί σύνδεσμοι λειτουργούν κανονικά.
- [ ] Οι κανονιστικές και οι ενημερωτικές αναφορές διαχωρίζονται.
- [ ] Το ιστορικό αλλαγών έχει ενημερωθεί.
- [ ] Η ιστοσελίδα δημιουργήθηκε με επιτυχία.
- [ ] Οι επίσημες μεταφράσεις προσδιορίζουν την ακριβή πρωτότυπη έκδοση.

## 26. Εξαιρέσεις

Μια προδιαγραφή ΜΠΟΡΕΙ να αποκλίνει από τον παρόντα οδηγό, όταν το θέμα απαιτεί διαφορετική παρουσίαση ή σημειογραφία.

Μια εξαίρεση ΠΡΕΠΕΙ:

- να είστε σαφείς·
- να έχει περιορισμένο πεδίο εφαρμογής·
- αναφέρετε τον λόγο·
- να διασφαλιστεί η διαλειτουργικότητα και η δυνατότητα επανεξέτασης·
- να εγκριθεί μέσω της συνήθους διαδικασίας εξέτασης.

Η ευκολία ή η παραδοσιακή μορφοποίηση από μόνες τους δεν αποτελούν επαρκή αιτιολόγηση για μια μόνιμη εξαίρεση.

## 27. Συντήρηση του παρόντος οδηγού

Ο παρών οδηγός διέπεται από την Πολιτική για τον κύκλο ζωής και την έκδοση προδιαγραφών του Οργανισμού Προτύπων Πληροφορικής (OMI).

Οι διορθώσεις του εκδοτικού τμήματος ΕΝΔΕΧΕΤΑΙ να κυκλοφορήσουν ως εκδόσεις patch. Οι συμβατές προσθήκες ΕΝΔΕΧΕΤΑΙ να κυκλοφορήσουν ως δευτερεύουσες εκδόσεις. Οι αλλαγές που καταργούν την καθιερωμένη δομή του εγγράφου, τους αναγνωριστικούς κωδικούς ή την ερμηνεία απαιτούν μια κύρια έκδοση.

Οι αλλαγές στον παρόντα οδηγό ΠΡΕΠΕΙ να αξιολογούνται ως προς τις επιπτώσεις τους στα εξής:

- υφιστάμενες προδιαγραφές·
- επίσημες μεταφράσεις·
- αυτοματοποιημένα εργαλεία·
- τεκμηρίωση σχήματος;
- εξωτερικές αναφορές·
- διαδικασία εργασίας των συνεισφερόντων.

## 28. Περίληψη

OMI Οι προδιαγραφές πρέπει να λειτουργούν ως κάτι περισσότερο από απλή επεξηγηματική κείμενο. Αποτελούν μακροπρόθεσμες τεχνικές συμφωνίες μεταξύ συγγραφέων, επιμελητών, εκδοτών, αποθετηρίων, προγραμματιστών λογισμικού, συστημάτων διατήρησης και μελλοντικών υλοποιητών.

Η συνεπής δομή, η ακριβής ορολογία, οι επαληθεύσιμες απαιτήσεις, οι διαρκείς αναγνωριστικοί κωδικοί, τα επαληθευμένα παραδείγματα και η υπεύθυνη συντακτική επιμέλεια αποτελούν, ως εκ τούτου, ουσιώδη στοιχεία του ίδιου του προτύπου.
